# H050 — Lead agent review

13 November 2026. The app shows local account records for discovered clients. The user can confirm the start of an official sign-in flow. The review covers the UI → strict IPC → discovery and pinning → account adapter → owned process → normal exit path. It assumes a single-user desktop app, three clients, and one sign-in flow at a time. The team applied Ponytail full and review and the existing design guide. The review scope covers the account flow.

<a name="düzeltilen-bulgular"></a>

## Resolved findings

1. **Returning to the screen canceled a sign-in in progress.** `src/features/integrations/Accounts.tsx:403` had an active-flow effect that stopped the running flow. A user could lose the sign-in after changing screens. The lead agent removed automatic cancellation. The UI now reconnects to the existing flow. Only the Stop action cancels it. A test reopened the screen and confirmed continued polling without a cancel IPC request.
2. **The app could replace a root process before it confirmed exit.** `src-tauri/src/integrations/accounts.rs:144` blocked new work only while a flow was pending. `src-tauri/src/integrations/accounts_windows.rs:392` could treat a process-query error as proof that the process closed. The app could lose ownership while the same root still ran. The fix blocks work during pending and cleanup_failed states. Stop reports success only after it confirms exit. The UI keeps the active flow visible and lets the user retry Stop with the same flow ID. Contract, lifecycle, and UI retry tests passed.
3. **The active flow was hidden when the launch reply was lost.** `src/features/integrations/Accounts.tsx:500` refreshed only account status. A user could not reach Stop after an IPC error if the official CLI remained open. Refresh reads the backend's active flow first. The test lost the launch reply, refreshed the view, found the active flow, and canceled it.
4. **Vendor commands that seemed passive wrote data.** Isolated real-vendor trials for `src-tauri/src/integrations/accounts_windows.rs:47` and `accounts_opencode.rs:111` showed that Claude wrote settings and a backup. OpenCode also changed its database. Automatic account reads could change user state. The product does not use the Claude command. For OpenCode, it reads only a bounded local provider record after it checks file identity. The DTO excludes secret values. It indicates whether a credential is present or absent. Source, parser, and no-spawn tests passed.
5. **The pin order allowed a namespace change.** `src-tauri/src/integrations/accounts.rs:165` now pins and checks the parent directory chain before it pins the executable. This prevents a launch from the wrong path if a directory moves or changes after the app verifies the executable. Existing discovery security regressions and the final Rust gate passed.
6. **The old UI acceptance depended on a fixed catalog count.** `tests/e2e/accessibility.spec.ts:5` found that the catalog contained 13 records, but the test expected 12. This caused a false alarm about a missing user-facing record. The test now checks that the current catalog renders every record. All 7 UI scenarios passed again with the same threshold.

## Visual and interaction review

| Before | After | Why |
| --- | --- | --- |
| Setup and routing cards were present. The account record was not separate. | One Accounts panel shows all three clients, a short status, and one official sign-in action. | This keeps sign-in separate from savings and routing success. |
| The user could not tell which auth method the sign-in would affect. | Confirmation shows the selected CLI and version. It shows the ChatGPT, Claude, or OpenCode method and warns that sign-in may change a record. | The user can see which sign-in method the action affects. |
| Refreshing the screen affected the sign-in lifecycle. | The flow continues when the user leaves the screen. Cancel is the first focus target. Focus returns to the trigger when the dialog closes. | This keeps user control during keyboard use and screen changes. |

The review checked Graphite tokens, light and dark themes, narrow views, and reduced-motion behavior. The engine, model, and measurement contracts stayed the same. Cosmetic preferences needed no further review cycle.
