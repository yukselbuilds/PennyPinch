# H051 — Code and interface review

13 November 2026. The lead agent closed H051 after local development acceptance on Windows 10 22H2 x64.

Sessions has separate Chats and Accounts views. The Windows adapter reads bounded metadata only from a trusted, existing Codex 0.167.0-alpha.4.1 server. With user confirmation, Headroom can open the official chat center. The user selects a chat and starts any new turn in the official client.

The lead agent reviewed `App → Sessions → sessionClient → manage_sessions → SessionManager → Reader/OpenedCenter`. The review included the source protocol and the new location of the `Accounts` view. It assumed one desktop user, one profile, and pages limited to 64 records. The scope covers the selected profile and bounded history.

The single Luna xhigh worker prepared the research, fixture presentation, and focused test helpers. The lead took over after confirming that the worker finished writing. The development worker and model stayed the same.

## Correctness and trust boundaries

- Before sending initialize, the adapter checks the kernel peer PID and holds a live process handle. It verifies the same user, a non-elevated token, the signature, and the pinned version. The short `--version` helper uses an environment without config or auth. Reading metadata starts no daemon.
- The lead checked the standard initialize effect on global identity and sign-in policy in the pinned source. The non-originator role uses only the allowed metadata calls. `useStateDbOnly:true` prevents scan and repair. For a new empty chat, the adapter calls `thread/read(includeTurns:false)` only for a missing identity from the loaded list.
- The DTO, logs, and persistent record exclude titles, previews, and history. Extra response fields may pass through bounded transport memory. The adapter requests only metadata. It shows the project basename and uses a scoped hash for the profile and UUID. Model labels alone establish neither identity nor a link to traffic.
- The app shows active or idle as live only with a loaded-list observation. The app distinguishes recorded chats from open chats. It shows ended only after an explicit `thread/closed` event, if the chat has not loaded again. Process loss leaves state unknown. When the source returns a cursor, the app marks the results as partial.
- Opening requires a single-use confirmation valid for 45 seconds. The app checks the same profile and kernel peer again and pins the executable again. The fixed command takes no prompt, model, provider, reasoning, or thread-ID argument. Releasing the normal client's process handle lets it keep running. Sign-in has a separate kill-on-close path.
- The source enriches `thread/list` with a live model, provider, and reasoning snapshot. A separate bounded read covers missing empty loaded records. This path avoids a query for each row. An unknown version or client remains unknown.

## Interface findings fixed

| Before | After | Why |
| --- | --- | --- |
| Account cards appeared inside Applications. | Sessions contains Chats and Accounts. | Connection settings, account status, and chat state each have their own purpose. |
| An old status could remain visible after a failed read. | The view clears the snapshot on error or when hidden. It labels the last observation separately. | The view shows which information is current. |
| An empty snapshot showed the generic client label three times. | The view keeps each platform name without a snapshot. | The user can identify the scope that is unknown. |
| An unnecessary read could disable the trigger after the dialog closed. | The timer skips its read while the dialog is open. | Cancel restores keyboard focus. |
| A successful automatic read could clear a launch error. | The view keeps the action error separate. Manual refresh clears it. | The user can see the result of the failed action. |
| The contrast check could start before the theme change finished. | The test waits for the font and two paint frames. | It checks the completed view with the same threshold, rules, and colors. |

## Evidence and remaining acceptance

The gate passed 221 Node contract tests and 441 Rust tests. It ignored 17 opt-in tests. Formatting, the frontend build, and the desktop build passed. The first frontend build had a visibility type narrowing error. The team fixed the React component. Node does not import that component. The other inputs matched, so the team reused the passing Node results.

Later edits only changed tests. They strengthened the ignored native opening check and made the UI test wait for the new theme to paint. Production sources stayed the same.

The final UI runs passed 6 chat scenarios, 3 account scenarios, and 4 general screen scenarios. The 122 accessibility audits found no violations. Navigation to the second paint frame had a p95 of 16.9 ms against a 250 ms threshold. That measurement applies to the isolated App fixture. OS DPI and native performance need separate evidence. The visual review used fixture renders in Turkish dark and English light.

The actual Codex tests checked metadata and identity, two chats with the same model, and server loss. The official client connected to the correct isolated server, kept its settings, and continued after the launching process exited. These tests made no real provider or subagent turn. The record for the first opening run separately describes public TUI startup checks and the screen reader preference. User settings stayed the same.

Final native acceptance passed in run `12e3ea28`. The UI showed three chats, including two with the same model, and separate Accounts and Chats views. Cancel left the client unopened. Confirmation opened the official center on the correct server. The client kept running after normal Headroom exit.

The three chats kept their settings and config. The run made 0 inference requests. Codex unloads empty chats when their owner exits. The final opt-in fixture therefore keeps the owner alive until the UI check ends. That change affects test setup only. Production sources stayed the same.

The current native opt-in test and formatting passed. The team reused the earlier gates with matching inputs. The first locked and empty-fixture attempts retained their failed results. The acceptance thresholds stayed the same.

**Decision. The review accepted the local scope and found no open correctness or security issues.** Windows 11, the new feature on macOS and Linux, other Codex versions and profiles, and Claude and OpenCode live metadata still needed verification. Live provider and subagent turns and the release package also remained open. The team ran no CI. Development token savings remained unmeasured.
