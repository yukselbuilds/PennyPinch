## Findings and fixes

1. **The release EXE used the console subsystem — closed.** `src-tauri/src/main.rs:1` had no Windows GUI attribute at startup. The actual release file had PE subsystem value 3. A normal start could create an extra console window. The team added the GUI attribute to the Windows release build. `tests/runtime/test_windows_release_executable.py:17` reads the actual EXE's MZ/PE, x64, PE32+, and GUI subsystem fields instead of searching source text. The test failed on the first candidate and passed on the new LTO-enabled candidate.

   `scripts/build-windows.ps1:22` runs the same check at the end of packaging. A finally block restores the process environment. The debug and other-OS build subsystems do not change. The team excluded the interrupted first candidate and test-driver failure from acceptance.
2. **The documents were missing or outdated — closed.** The user guide was missing. The README described the local Windows 10 update/rollback as future work. The team created the guide and updated the README. The documents explain Connect, engine Start, the connected route, and the scope of external verification. They describe what the local input percentage measures. Billing, model support, and subagent support need separate evidence.

The team used the Emil guide to review the existing hierarchy and interactions. CSS and design stayed the same.

## Package and native acceptance

The default release profile has LTO enabled, 1 codegen unit, stripping enabled, and panic abort. The team installed the real NSIS/LZMA package under a separate QA identity. The 22,333 resource files matched the expected inventory. The first corrected runner stopped at raw hash comparison. It did not account for the three-byte package-type marker that Tauri writes to the packaged EXE. The team read the pinned `tauri-utils 2.10.2::platform` source and applied the single `__TAURI_BUNDLE_TYPE_VAR_UNK → __TAURI_BUNDLE_TYPE_VAR_NSS` transform. That transform produced the full expected file. The team compared it byte-for-byte with the installed file. The verifier rejected all other byte differences. This was a runner assumption, not a product defect. The team retained the failed record.

With discovery debug tracing off, the team added an empty, unexecuted OpenCode file to the real installation. The user clicked **Open** once to confirm the Windows file picker’s prefilled path. Automation entered the path.

The lead agent used the native accessibility API to perform three complete scans, open Activity and return, then read the retained manual source row again. One OpenCode installation and the manual source remained. No error or stale banner appeared. The checks used the actual native window without mock transport, CDP, or debug tracing. It did not repeat native file-picker cancellation in this run. Frontend/Rust tests cover cancel and race contracts. Canceling exit kept the app and row. The second confirmation closed the process with code 0. The test did not observe discovery tracing.

The primary tool reported a screen/geometry error. The team used Open Computer Use as an alternative for accessibility checks. Some background captures showed the foreground Codex window, so the team did not use them as evidence. The checks bind to the target Headroom PID/window tree and owned-process record. The team programmatically bound source/NSIS/installed-file/test fingerprints.

The normal uninstaller removed the QA installation with code 0 and cleaned QA state and the sidecar lock. The team kept artifacts from the interrupted first candidate under the project `work` root.
