## State at the review date

The app scans automatically, remembers prior connection choices, and can start the engine during Connect. Normal setup requires no terminal, manual config edit, port selection, or per-model setup. The app keeps Advanced diagnostics closed by default. CLI and Desktop validation choices made during development are not daily-use steps.

However, starting the engine alone does not route traffic from clients that are not connected. The user must change one setting once. When the scan finds multiple installations, the resolver does not choose by itself. Installation selection is therefore not limited to developer tests. The working first-use flow and a finished, smooth daily-use experience are at different stages.

## Target experience

1. **First open:** List discovered Codex, Claude Code, and OpenCode in simple rows. Show the applications to connect and a short impact summary. One explicit **Connect and start** action prepares the selected scope and applies a reversible setting change. Show each application's result separately. Do not report all clients as connected if one fails.
2. **Later open:** Keep prior choices. **Start** is enough. Do not ask the user to select a CLI, Desktop, version, or model again. Do not run an automatic paid test. Do not connect a newly discovered application until the user selects it. If an open client still uses an old setting, show only the required reopen step.
3. **Daily screen:** Show one main control, short application states, and platform → model usage and savings for the same period. Show savings as tokens and a percentage. Show cost only when a reliable source exists. Use short text to separate engine ready, route recorded, and traffic observed. A green engine state alone does not prove savings.
4. **Sessions:** Use the real metadata paths from H050/H051 for account connections and open chats. Do not infer session or model ownership from an operation name. Do not add tabs or secondary panels only to fill space.
5. **Advanced:** Keep version, CLI/Desktop binary, endpoint, settings ownership, detailed compatibility, and optional real verification here. Do not make each user connect each model or subagent. Cover requests on the same supported route independently of model name. Show an unverified route or agent scope as unknown.

Keep Graphite colors and the current technology. A new theme, framework change, second dashboard, or sample savings data is not required.

<a name="kabul-senaryoları"></a>

## Acceptance scenarios

- New user: After automatic discovery, establish a supported normal connection without selecting a command, config, port, or binary. Explain and allow reversal of the one-time change.
- Returning user: Do not ask for the same verified scope again. Do not silently switch to another installation when the saved installation is missing or changed, or when the user config conflicts.
- CLI + Desktop: Use one logical row only when evidence confirms a shared effective scope. Offer a short, useful choice when the scopes differ. Do not assign one surface's traffic evidence to another.
- Operation failure: Keep successful, pending, and failed applications separate. Make retry and removal explicit. Preserve current model, auth, and reasoning settings.
- Measurement: Distinguish absent data, incomplete data, 0, and increases. Calculate tokens and percentage for the same scope. Show platform/model and chat breakdowns only with proven attribution.
- Closing: Before H030 completes, do not claim that closing the window keeps the app in the tray or keeps the connection active. Do not hide the risk of a persistent endpoint with a stopped engine. Test pause, engine stop, and connection removal as different actions. Do not promise an automatic return to direct connections without evidence.
- Keyboard/scaling: Keep the main action and recovery visible and accessible. Long diagnostics must not hide normal navigation. Define control measurements before the implementation slice.

## GitHub and platform verification

Read-only observation on 3 November: origin was reachable. Remote main matched local origin/main. Local main was 6 commits ahead. Git did not track 18 of 56 changed or new files. This review did not commit, push, or dispatch Actions.

The only current workflow was `.github/workflows/source-checks.yml`. It ran frontend tests and a build on standard Ubuntu 24.04 after a manual start with `free_only_confirmed`. It was not a native Windows/macOS/Linux matrix. H048/H049 already covered macOS/Linux porting and validation. The review found no need to open a new task.

At the review date, standard runners were free for public repositories. Private repositories had an included usage limit. Do not start another native run until you recheck the current free quota and hard stop. Success on a standard Windows x64 runner alone does not prove Windows 10/11 x64 desktop compatibility. A Windows 11 ARM runner has a different architecture and cannot replace the x64 target. CI can provide build, package, and isolated runtime checks. Real client accounts, Desktop adoption, and full interactive use need separate evidence.
