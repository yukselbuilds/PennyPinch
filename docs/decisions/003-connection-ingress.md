# 003 — Stable client ingress

The decision was first recorded on 20 October. By 21 October 2026, Option 1 was implemented and H040 had passed local acceptance on Windows 10. The endpoint/relay, RuntimeManager, pinned engine, and native UI action → manager → engine path were reviewed. The final full Rust gate had 68 PASS / 2 opt-in ignored, and the embedded build passed. [Final acceptance](../reviews/H040.md), [evidence](../proofs/connection-ingress.md), [failure matrix](../validation/ingress-failure-matrix.md). This is not live client/model/authentication or release support.

<a name="seçilen-mimari"></a>

## Selected architecture

Option 1 uses a stable Rust-owned client TCP ingress that listens only on `127.0.0.1`. The existing H006/H014 Python engine keeps its own dynamic loopback port. Rust pins each client TCP connection to one verified `backend_generation` and relays the bidirectional byte stream opaquely. No new Headroom proxy, HTTP parser, TLS termination, header/body rewrite, auth forwarding or translation, or direct upstream path will be added. This is not a second Headroom engine.

This decision is limited to `http://127.0.0.1:<kalıcı-port>` for local Windows application processes, a stable endpoint across engine restarts, and verified API/HTTP fixture routes. ChatGPT gateway/OAuth, HTTPS-to-local, HTTP/2, TUI, and unknown auth/upstream paths remain separate capabilities marked `unknown/not_tested`. There is no automatic direct fallback for them. This ingress design does not prove that CCR/prefix history remains available after an engine restart.

<a name="mevcut-kaynak-bulguları"></a>

## Current source findings

`src-tauri/src/runtime/manager.rs` owns controller/helper/engine identity, dynamic `listener_port`, and `runtime_generation` within a single actor. Startup does not become ready until the process chain, TCP listener PID, and pinned `/readyz` check agree. Ownership and readiness are rechecked during health checks. Stop verifies the generation-bound stdio event, bounded exit, engine listener closure, helper/engine absence, and an empty Job Object. A forced result is not graceful. In the H040-b integration, stop first removes the ingress route, then stops the engine, and completes or cancels remaining relay connections within a bound. A separate ingress snapshot distinguishes endpoint identity/address from backend generation. Runtime schema 1 is unchanged. Stop and shutdown response budgets are 90 seconds.

`runtime/desktop_controller.py` runs the H006 console-free controller → hidden helper process and generation correlation. `work/proofs/packaging/headroom_runtime.py` selects `free_loopback_port()` for every engine start and starts the pinned engine with `--host 127.0.0.1 --port <port>`. Listener PID and readiness are verified. Selecting the port before binding leaves a race window, but a new generation is accepted only after the correct engine PID owns it. The current STOP_EVENT_TIMEOUT and PROCESS_EXIT_TIMEOUT are 30 seconds each, and the port-close check is 3 seconds. Actor stop/shutdown response budgets, which include ingress drain, are 90 seconds.

<a name="alternatifler"></a>

## Alternatives

| Option | Result |
| --- | --- |
| **1. Stable Rust TCP ingress + dynamic engine backend** | Requires no new HTTP parser or Go/Rust dependency. Rust relays new connections as byte streams to the verified backend. The endpoint port remains independent of the engine generation. Independent relay/drain and peer-PID behavior were tested with local fixtures. The manager's real process/job/generation binding and app-exit timing still require separate testing. **Selected.** |
| **2. Make the engine port stable** | This appears to reduce layers, but clients connect directly to the Python proxy port. The address is unavailable while the engine is stopped or reconnecting. If another process takes the port, a credential-bearing client request could reach it. Rust cannot prevent that before startup. The manager's temporary-port readiness/ownership flow would also change. A stable port alone does not meet H040's security requirement. |
| **3. Rust HTTP reverse proxy** | It could provide features such as synthesizing HTTP statuses or URL routing, but would require HTTP parsing, keep-alive/request framing, header/transfer encoding, SSE flushing, and error semantics. Normalizing or buffering headers/body could break auth/model/reasoning or streaming. It adds unjustified scope and risk against H040's byte-preservation priority. It can be reconsidered if a concrete HTTP need is established later. |

<a name="windows-bind-koruması-ve-yerel-sonuç"></a>

## Windows bind protection and local result

On Windows, `SO_EXCLUSIVEADDRUSE` is set before bind. The listener is created with `WSASocketW` using `WSA_FLAG_NO_HANDLE_INHERIT | WSA_FLAG_OVERLAPPED`. The option is set before bind/listen, and an owned guard balances the `WSAStartup` reference. Using `TcpListener::bind` alone does not prove that this policy is applied.

As a positive control, two fixture sockets bound and listening on the same loopback address were able to share it with `SO_REUSEADDR`. The same contender bind was rejected against the production exclusive listener. The earlier short plain-`TcpListener` + reuse-only probe was also rejected. That result alone is not evidence of a takeover vulnerability and is not presented as such. Broader Winsock behavior is limited to the tested Windows 10 host.

`connection-endpoint.json` contains only fixed schema 1, `127.0.0.1`, port, UUID endpoint ID, and revision. On first launch, while an exclusive listener holds port 0, a `create_new` temporary file in the same directory is flushed/synced and published with `MoveFileExW` no-replace/write-through. Later launches load and bind the same port. If it is occupied, the operation returns conflict and the record remains unchanged. The record is limited to 1 KiB, the struct enforces exact fields and rejects duplicate fields, and reparse checks are applied.

For an established backend socket, the Windows TCP owner table is queried for the exact server-side local/remote IPv4 4-tuple. Forwarding does not start unless there is exactly one row and it has the expected engine PID. Missing, ambiguous, non-loopback, or wrong-PID results fail closed. This check runs after TCP connect but before any client application byte is read or sent. A race can still establish a TCP connection to a foreign listener. The contract is to send no auth/application payload to a foreign process, claim no ownership over it, and never terminate it. A valid PID was verified in a local fixture. A separate test child listener was rejected for the wrong PID and remained alive without receiving payload. H040-b binds this lease to the manager's process/job handles and generation.

After an accepted TCP connection closed, the same endpoint port could immediately be rebound with `SO_EXCLUSIVEADDRUSE`, and the recorded port remained unchanged. This was a host test that closed one connection and reopened it within the same process. It does not prove long-lived keep-alive behavior, application process restart, another Windows version, or a real manager restart. When the app is fully closed, the socket is released. Another process could take the port, and the next launch must fail closed without changing the address.

The socket implementation follows the Windows Winsock API contracts. [SO_EXCLUSIVEADDRUSE](https://learn.microsoft.com/en-us/windows/win32/winsock/so-exclusiveaddruse), [SO_REUSEADDR and SO_EXCLUSIVEADDRUSE behavior](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse), [WSASocketW no-handle-inherit flag](https://learn.microsoft.com/en-us/windows/win32/api/winsock2/nf-winsock2-wsasocketw), [setsockopt](https://learn.microsoft.com/en-us/windows/win32/api/winsock/nf-winsock-setsockopt), [bind](https://learn.microsoft.com/en-us/windows/win32/api/winsock/nf-winsock-bind). This slice uses the pinned `windows-sys 0.61.2` crate.

<a name="giriş-ve-sahiplik-sözleşmesi"></a>

## Ingress and ownership contract

- On first launch, Rust binds `127.0.0.1:0` and atomically publishes the selected port to the endpoint record while keeping the socket open. If the write fails, the listener closes and no client address is published. Later launches bind exactly the recorded port. If the port is occupied, the operation fails closed with `endpoint_conflict`. It does not choose another port, probe/claim/kill a foreign PID, or silently change client config.
- The endpoint record is stored only under `work/app-state/runtime` in debug builds and under the application's `app_data/runtime` root in release builds. It contains fixed schema, `127.0.0.1`, port, opaque endpoint ID, and revision/fingerprint. It contains no PID, backend port/generation, auth, request, workspace, or full user path. Its implementation follows the existing H015 store pattern for ancestor/reparse containment, bounded JSON, fingerprint-CAS, and temp `create_new` plus flush/write-through atomic replace. Concurrent first writes or a second app instance produce conflict. State is preserved on bind conflict.
- `endpoint_id`/endpoint port is the persistent connection address. `backend_generation` is a transient generation ID that changes after every successful engine start. These are separate fields/contracts. The engine's `listener_port`, PID, and generation are not exposed to clients or written to the persistent endpoint file. If needed, a separate content-free `get_ingress_snapshot` reports endpoint and backend state. Arbitrary fields are not added to the existing runtime snapshot.
- Rust ingress may open its accept socket before the engine. If no backend route exists, new client connections are closed without reading a byte. `ready` is returned only after the stable listener is open and the current pinned engine process/job, PID-owned backend listener, exact version/profile, and `/readyz` have been verified and atomically published in the route table. After every new backend TCP connect, the owner 4-tuple is verified before any client payload is sent. No application/auth bytes are sent to a foreign listener. This does not guarantee that a SYN/connect can never occur.
- Each **TCP connection** is pinned to one `backend_generation`. The boundary is the TCP connection. Every request on an HTTP/1.1 keep-alive connection stays on the same backend socket/generation. When the generation changes, an existing socket is not moved to the new engine. Its old stream completes or closes. New connections use the new healthy generation. A disconnected/partial SSE or POST is not replayed automatically. There is no second backend POST for the same request. Client retry behavior is not guaranteed by the app and is observed in a separate fixture.
- The relay only streams `TcpStream` bytes. Chunk/segment boundaries need not match, but the concatenated byte sequence and order are preserved. A fixed-size buffer with offsets and a nonblocking pump in both directions handles partial writes/backpressure. Body/header/CRLF/SSE content is not parsed or stored. The delayed-reader fixture completed a 4 MiB transfer byte-exactly, but `WouldBlock` was not observed on Windows loopback. This local test is not evidence of prolonged kernel-level backpressure. `active_connection_count` counts TCP connections. It is not presented as an HTTP stream/request count.
- Each `BackendTarget` route snapshot carries the backend loopback port, generation, expected engine PID, and liveness lease. After connecting and before reading even one client byte, the Windows TCP owner table verifies the server-side PID for the **exact established 4-tuple**. Both sockets are closed if the table is ambiguous or missing. The H040-b lease is bound to weak manager-owned job/process handles and an immutable generation. Revoke or loss of owned process/job membership fails closed. Relay sessions do not extend the job's KILL_ON_JOB_CLOSE lifetime.
- Both directions have bounded concurrent connection caps, connect timeout, idle timeout, and lifetime deadline. Defaults are 32 TCP connections, 2 s connect, 300 s idle, and 8 hours lifetime (with hard caps of 64 connections and 24 hours). Fixtures test boundary behavior with shorter deadlines. Suitability for normal SSE idle periods has not been measured separately. Cap overflow or a missing backend produces a fixed content-free state/error. Because the TCP relay is opaque, Rust does not synthesize HTTP 503. It rejects/closes the connection without sending bytes.
- The H040-b actor coordinates engine restart and stop. It sets the ingress route to `none` and accepts no bytes from new connections. The manager starts the current engine's request-aware graceful shutdown so completed keep-alive requests can close. Ingress waits a bounded time for existing relay connections to finish. If the drain deadline expires, remaining relay connections are terminated and the result is `incomplete/cleanup_failed`, not graceful success. The manager then closes the old generation using PID/port/job evidence. No new engine starts until the process tree is fully closed. After readiness/ownership of the new pinned engine, the route changes atomically to the new generation. The actor stop/shutdown response budget is 90 seconds. A second start/stop must not begin while the actor is still processing the first operation. Native idle HTTP keep-alive stop was measured in H040. Active gated-SSE stop with the pinned engine remains open in H029/H030.
- **When the application exits completely**, Rust releases the listener socket. If client config still points to that port, another process under the same user could take it. Opaque TCP alone cannot prevent this while the application process is absent. H040 can prove protection across engine restarts. Complete app-exit protection requires keeping a tray/background process alive (H030/H034) or first removing the client config connection. Until this lifecycle is resolved, do not claim that the endpoint is protected from attacks/another listener while the app is closed.

## H040-c pinned-engine lifecycle smoke (21 October 2026)

The opt-in test `runtime::manager::tests::live_manager_stable_ingress_survives_pinned_engine_restart` completed against the pinned runtime payload with **1 passed, 0 failed** (36.66 seconds). It verified the same stable endpoint ID/port, two real engine generations, `/readyz` through ingress, a health observation longer than 5 seconds, duplicate start returning the same generation, rejection of stale-generation stop, closure of the owned engine port, and continued liveness of a test-owned foreign listener. During stop, the endpoint remained bound but had no route. A no-route connection received no application response byte. Windows can close early with `ConnectionReset`, so the test accepts only fixed socket-close errors as an empty close. A timeout or response byte is not a pass.

At real engine startup, the Job Object contained 5 active processes. The three expected held controller/helper/engine handles passed individual job membership, liveness, generation, parent-chain, and exact listener-owner checks. The other two members were console-host processes. Production now requires `active_processes >= 3` while retaining individual validation of the three expected handles and their membership. It does not infer ownership by process name/basename. Successful route publication also refreshes the endpoint-ready observation time, so an earlier endpoint heartbeat cannot expire during long startup and incorrectly leave a ready route `unknown`.

Evidence is limited to Windows 10 x64 build `10.0.19045.0`, Rust/Cargo `1.92.0`, and the pinned local runtime. The test made no provider/auth/model call. It is not evidence for a real Responses/Anthropic upstream, CCR, live-engine gated-SSE stop, HTTP keep-alive stop, client compatibility, app exit/tray, Windows 11, or a clean machine. Separate opaque relay fixtures are covered by H040-a2. Source/command/pinned-payload hashes and the bounded diagnostic/cleanup summary are in [`pinned-smoke.json`](../../work/proofs/connection-ingress/pinned-smoke.json). The environment/command fingerprint is `9bc3c407ea961f575ab3f485e4149b2cd1fd371e23c7bc69d2943b2b75d7a8d4`.

<a name="h040-a2-yerel-relay-dilimi"></a>

## H040-a2 local relay slice

`src-tauri/src/runtime/ingress_relay.rs` provides an opaque TCP relay on the stable listener using a generation-pinned `BackendTarget`. Each new TCP connection receives one backend port/PID/generation lease. Route changes do not move open connections. After connecting to the engine socket and before reading client payload, the exact server-side TCP 4-tuple owner PID is verified. A 40 ms bounded visibility wait is used only for a missing TCP owner row. Known mismatch, ambiguous tuple, or owner-table error fails closed without retrying.

The relay does not parse HTTP/SSE, log the byte stream, modify auth/model/reasoning fields, or create a second backend request. A single bounded pump uses fixed buffers and partial-write offsets in both directions. It handles partial writes/backpressure, half-close, connect/idle/lifetime deadlines, and the connection cap. `begin_drain` closes the new route. `finish_drain` waits a bounded time for natural completion and cancels active sockets on timeout. `DrainReport.graceful` remains false if cancellation occurs. `shutdown` releases the listener only after the accept thread exits within the bound.

Focused synthetic TCP fixtures test Responses/Anthropic-like HTTP bytes, a gated SSE delta arriving before the terminal frame, an existing connection remaining on its old generation, no replay after partial SSE, byte-exact completion of a large response for a delayed reader, half-close, cap/deadline/cancel behavior. In the delayed-reader fixture, the client set and verified `SO_RCVBUF=2048` before connecting. The backend wrote a 4 MiB response after receiving request bytes, the client delayed reading for 180 ms, and the full content arrived. A separate bounded diagnostic writer also measured `SO_SNDBUF=2048` with `WouldBlock=0` on the same host. Therefore this evidence is not proof of prolonged kernel-level backpressure or performance. It demonstrates only byte-exact 4 MiB transfer to a delayed reader. Real backpressure/performance must be measured separately. A separate real child-process listener fixture is rejected for the wrong PID and remains alive without receiving client payload. These results do not establish Responses/Anthropic compatibility of the pinned proxy or paid-provider behavior.

The independent H040-a/a2 endpoint/relay fixtures remain local acceptance evidence. The H040-b integration test additionally binds the manager-held process/job handles, actual `backend_generation`, and route lease.

<a name="h040-b-runtimemanager-entegrasyonu"></a>

## H040-b — RuntimeManager integration

In the local H040-b candidate, the actor owns the `StableIngress` and `IngressRelay` lifecycle. The route lease is bound to weak manager-owned job/process handles and generation. Relay sessions do not extend the job's lifetime. Readiness requires matching controller/helper/engine ownership, health/readiness, listener route, and generation. When the engine stops or is lost, the route is removed first. Stop ordering is begin-drain → graceful stop of the pinned engine → bounded finish-drain → owned-cleanup verification. An incomplete drain is not graceful. Only unverified owned cleanup blocks restart.

Without changing runtime DTO schema 1, `get_ingress_snapshot` returns a separate snapshot with the stable endpoint ID, loopback address state, backend status, generation, error and nullable `active_connection_count`. PID, raw engine stdout, auth, and content are not exposed. The Tauri command is registered. The connection-plan consumer for this new snapshot is added in H017. The existing Start/Stop UI → manager → ingress/engine path passed H040 native acceptance.

The focused manager suite recorded 18 passes and 1 ignored real pinned-engine smoke test. The suite covers DTO/correlation boundaries, stale health lowering ingress readiness, duplicate start, stale-generation stop, actor lifecycle/error/cleanup, and fail-closed port conflict. The final relay suite candidate passed 13 tests covering opaque HTTP bytes, gated SSE, connection-generation pinning, no replay, delayed-reader byte-exact 4 MiB, no route, cap/deadline/drain, and a foreign listener that remains alive after receiving 0 bytes of payload. `cargo check --offline` and `cargo fmt -- --check` passed. Cargo check reported only existing dead-code warnings for unused methods/fields. The full local quality gate was not run in this slice.
