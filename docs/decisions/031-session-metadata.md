# H051 — Chat metadata and lifecycle

13 November 2026. H051 was accepted for local development on Windows 10 22H2 x64. H050/H026 dependencies were accepted. H049 was deferred by user decision. No Actions, new real sign-in, or model request was started for this task.

<a name="amaç-ve-sınır"></a>

## Purpose and limits

Show chat metadata separately from account records, and show runtime state only when the source is trusted. Do not collect title/preview, user messages, responses, tool output, auth, or conversation history. Use only the minimum client/chat/project/time/parent/model metadata required. Starting a new server, adding hooks, restarting an existing daemon, or changing client config is not discovery and is never done automatically.

File or process presence does not prove that a chat is open/running/ended. Distinguish loaded-idle chat, working turn, waiting, not-loaded record, and unknown. A dropped connection does not mean every chat has ended. The latest metadata update is not Headroom traffic. Show traffic/savings only when the same request/chat identity is evidenced. Do not match by model name. Preserve H026's existing route/opaque-identity semantics.

## Existing research

- Pinned the installed Codex `0.167.0-alpha.4.1` official help, its generated JSON schema, and sources at the same tag, `d2c035639366e0bf2c316aa2065c24aabc12bcdc`. The schema includes model/reasoning/parent and runtime status in Thread metadata. The proxy forwards WebSocket bytes to the existing AF_UNIX socket. It is not a JSONL client. The product connects directly to the existing socket and does not start a daemon or chat client. Initial version verification can use the existing Discovery helper to run a short `--version` process with a cleaned environment that loads no auth/config. Later reads use the same live process handle. Verify the Windows kernel peer PID, same SID/unelevated token, and trusted real Codex exe version before any application data. Do not send initialize to an unknown version. The live process handle prevents PID reuse. Do not rehash the initial signature on every refresh of the same live process.
- The [official app-server documentation](https://learn.chatgpt.com/docs/app-server) notes that the default `thread/list` may scan/repair JSONL. The product's passive reader cannot use that mode. `useStateDbOnly:true` is required. Enrich loaded chats in the list with live model/provider/reasoning from `thread_enrichment` snapshots. A new loaded chat with no messages may be absent from the DB list. Call `thread/read(includeTurns:false)` only for missing identities returned by the loaded list, then recheck the loaded list. Do not send `true` because it can load and persist history. The metadata API response may contain extra fields such as preview. They pass through bounded transport memory but are not retained in the typed parser or copied to DTO/log/state. Do not request message history.
- Make client profile/server scope explicit. A default CLI daemon does not represent all other Desktop profiles. If there is no safe existing endpoint or supported version, status remains unknown. Do not start an installation or login automatically.
- Pinned initialize source showed that the normal clientInfo name changes the process-global originator/user-agent and gateway-login policy. The reader uses this version's non-originator `codex-backend` role, `title: Headroom metadata observer`, and its own version. Send only initialize/initialized, `thread/list(useStateDbOnly:true)`, `thread/loaded/list`, and the metadata-only missing-record read described above. Do not send turn/start, resume, auth, or settings requests. This role grants no auth privilege and does not claim ownership of the existing client identity. User-agent preservation was verified in an isolated experiment on the real version with three empty chats.
- Presence in the thread list does not mean a chat is open. Idle plus the latest loaded-list witness means open. Active plus a loaded witness means working/waiting. notLoaded means recorded. If open/working metadata exists but the loaded witness disappears, state is unknown. Mark ended only for an explicit thread/closed event when it has not been loaded again. Do not infer ended from a closed process or dropped query. If there is a cursor, scope remains partial. The production path does not prove request/chat traffic linkage, so do not assign tokens/cost/savings to a row.
- Claude Code/OpenCode research is complete. Pinned sources are under `work/research/h051/vendor/`. No trusted passive Claude live-state contract was proven. OpenCode V1 `/session/status` is only the relevant server's in-memory map. It cannot distinguish absent/idle/ended, and starting a new server is not passive. This initial path remains unknown for those clients. That does not mean model/engine support is absent. Real user auth/JSONL/DB files were not read in the research.
- For official opening, Codex `agents --remote unix://` presents the existing server's chat center and does not accept a starting prompt/image. The user selects a chat in the official client. Headroom creates no per-row resume or model/provider/reasoning arguments. Opening requires a one-use 45-second confirmation for the current snapshot, the same profile/live kernel peer PID, and a trusted exe repinned at launch. The working directory is the existing disk root without config/AGENTS. The user selects a new task folder in the official client. Opening is disabled if no safe root exists. The ordinary client launched by ShellExecute is tracked only by its process handle. Unlike the kill-on-close login process, it is not killed when Headroom exits.

## Limits and first real evidence

- At most 64 rows per page. The DB and missing-loaded-record total is at most 128, and the normalized-row limit is 256. If a cursor exists, show partial/lower-bound scope explicitly. WebSocket messages are limited to 1 MiB, notifications to 32 per RPC, connect to 2 seconds, and socket I/O to 8 seconds. OS signature/file verification is not cut off by this I/O budget. Do not claim account/server or whole-computer coverage.
- `manage_sessions` runs only in the main window. Its schema accepts no URL/exe/model/auth/chat text. Records are held in RAM. There is no persistent chat inventory. Refresh every 10 seconds on the visible `Sohbetler` (“Chats”) screen. Errors or invisibility clear old live claims. Latest traffic and savings assignment remain unknown.

## Implementation and acceptance path

The lead agent owns process/endpoint/settings ownership, model/provider preservation, and traffic-attribution decisions. First establish the existing safe metadata path and evidence of no side effects. Then use a narrow versioned adapter → manager/strict IPC → simple UI. Offer official open/resume only through a user action and only when sources show model/reasoning/provider/scope preservation. No automatic message or hidden history transfer. The lifecycle of a chat opened for the user is not treated as equivalent to Headroom's short sign-in console.

Normal acceptance covers multiple chats, two chats using the same model, main/subagent relationship, and a quiet but loaded chat. Error/boundary cases include missing/disconnected endpoint, stale result, not-loaded record, closed process, unknown version, oversized/malformed response, extra/secret fields, and identity conflict. Fixture runtime behavior is not live-provider acceptance. Test real metadata/open/lifecycle separately on supported surfaces. Keep missing external coverage open.

Run focused tests with the existing pnpm/Rust tools. On the last-reviewed candidate, run the full local WORKFLOW.md gate once and perform the relevant UI/native checks. Record before/after source/config/tool/environment fingerprints in the same verification step. Do not rerun unchanged successful H050 checks. Do not transfer acceptance between operating systems. Model support is not limited to the developer worker's model.
